## 1. Мета використання AI

Метою взаємодії з GitHub Copilot було створення спеціалізованого AI-агента Build Engineer, який автоматизує підготовку кросплатформного C++ проєкту, налаштування CMake, GoogleTest/CTest та GitHub Actions.

Агент мав виконувати послідовність команд:

`git-init → create-project → create-build → create-actions → check`

Також необхідно було перевірити повторний запуск агента, його здатність виявляти помилки та коректність роботи CI/CD на Windows, Linux і macOS.

Нижче наведено основні етапи взаємодії. Дослівні промпти виділено окремо; початкові запити, повний текст яких не збережено, описано за їхнім змістом.

## 6. Проблема з CMake та компілятором MinGW

**Проблема:** під час першого налаштування і складання проєкту виникли труднощі з доступністю CMake. Після встановлення CMake та додавання його до PATH команди конфігурації стали доступними.

Однак наступна спроба складання через MSYS2 UCRT64 завершилася помилкою компонувальника:

```
collect2.exe: error: ld returned 116 exit status
```

**Дії AI:** Copilot повторив складання, перевірив компілятор і спробував виконати компіляцію безпосередньо. Помилка повторювалася.

Після аналізу доступних інструментів було вирішено використати Visual Studio 2022 з компілятором MSVC.

**Рішення:** створено окрему конфігурацію складання `build-msvc`, яка використовує генератор Visual Studio 2022.

**Результат:** програму й тести успішно зібрано. Тест `BasicAddition` пройшов перевірку.

**Висновок:** AI-агент не приховав помилку складання, а визначив альтернативний доступний інструмент і продовжив виконання після перевірки.

## 7. Створення та виправлення GitHub Actions

**Запит до AI (змістовий переказ):** налаштувати GitHub Actions для автоматичного складання й тестування програми на Ubuntu, Windows і macOS з використанням наявних CI-скриптів.

Copilot створив workflow із матрицею:

- `ubuntu-latest`
- `windows-latest`
- `macos-latest`

Після першого push workflow не запустив жодної job через проблему конфігурації.

Після виправлення workflow наступний запуск показав:

- Ubuntu — успішно.
- macOS — успішно.
- Windows — помилка.

**Причина помилки Windows:** CMake не зміг знайти необхідний екземпляр Visual Studio для вибраного генератора.

**Виправлення:** Copilot скоригував Windows CI-скрипт для використання доступного компілятора й середовища GitHub Actions.

**Кінцевий результат:** усі три job завершилися успішно. Збережено три Artifacts із виконуваною програмою для відповідних операційних систем.

## 9. Повторний запуск init

**Мета:** перевірити ідемпотентність агента, тобто здатність повторно виконувати ініціалізацію без пошкодження готового проєкту або створення зайвих файлів.

Для перевірки створено локальну гілку `demo/agent-verification`.

Спочатку під час спроб запуску `/init` Copilot виконував вбудовану процедуру налаштування агентських інструкцій `agent-customization` замість користувацького сценарію.

У результаті змінювався файл `.github/copilot-instructions.md`, а повний цикл ініціалізації не виконувався.

**Виправлення:** обрано Local-сесію VS Code і агента Build Engineer. У списку Workspace Prompts знайдено команду `init`.

Під час запуску через Local команда виконала початкові етапи, але зупинилася на `create-build` через раніше виявлену помилку MinGW:

```
collect2.exe: error: ld returned 116
```

Після цього було надіслано уточнювальний промпт:

> Continue the current /init workflow from stage 3 (create-build). The MinGW linker failed with exit code 116. This is a known toolchain issue. Use the existing Visual Studio 2022 MSVC build directory (build-msvc) instead of the MinGW build directory.

У тому самому запиті агенту було доручено продовжити `create-actions` і `check`, не змінювати вихідні файли та не виконувати Git commit, push або merge.

**Результат:** усі п'ять етапів завершилися успішно:

1. `git-init` — Passed.
2. `create-project` — Passed.
3. `create-build` — Passed.
4. `create-actions` — Passed.
5. `check` — Passed.

Тест `BasicAddition` пройшов успішно. Файли проєкту не були змінені, а стан Git залишився чистим.

**Висновок:** підтверджено повторне виконання сценарію без небажаних змін готового проєкту. Також виявлено важливість правильного вибору середовища запуску.

## 10. Перевірка check з навмисною помилкою

**Мета:** перевірити, чи агент може виявити неправильний результат тестування.

У файлі `tests/test_addition.cpp` тимчасово змінено очікуване значення:

```cpp
EXPECT_EQ(add(2, 3), 6);
```

Хоча функція `add(2, 3)` повертає `5`, тест очікував `6`.

Для перевірки використано такий промпт:

> Read and execute the verification procedure defined in `.github/prompts/check.prompt.md`. This is an intentional negative test for Laboratory Work No. 1.

Агенту додатково було вказано перебудувати тест, виконати CTest і повідомити про помилку, не виправляючи вихідний код.

**Результат перевірки:**

```
Actual value: 5
Expected value: 6

0% tests passed, 1 tests failed out of 1
1 - BasicAddition (Failed)
```

Copilot правильно визначив невідповідність між очікуваним і фактичним значеннями та повідомив про невдалу перевірку.

Файл тесту не було автоматично змінено агентом.

**Висновок:** команда `check` коректно реагує на помилки й не повідомляє про успіх у разі проваленого тесту.

## 11. Відновлення тесту

Після негативної перевірки очікуване значення повернуто до правильного:

```cpp
EXPECT_EQ(add(2, 3), 5);
```

Виконано повторне складання тестової програми та запуск CTest у Debug-конфігурації.

**Результат:**

```
1/1 Test #1: BasicAddition ... Passed
100% tests passed, 0 tests failed out of 1
```

Git-статус підтвердив відсутність незбережених змін у робочій гілці.

## 12. Обмеження та спостереження

У процесі роботи виявлено такі особливості:

1. GitHub Copilot може вибирати вбудовану процедуру `init` замість Workspace Prompt з аналогічною назвою.
2. Для виконання створених prompt-команд у використовуваній конфігурації VS Code знадобився Local-режим.
3. Налаштування компілятора залежить від операційної системи та середовища запуску.
4. Синтаксичні або статичні перевірки конфігурації не замінюють фактичного виконання GitHub Actions.
5. Під час окремої локальної перевірки YAML-бібліотека PyYAML була недоступною, тому повний парсерний аналіз YAML не проводився.
6. AI-агент потребує контролю з боку користувача, особливо під час редагування файлів та виконання Git-команд.

Проведено локальні перевірки складання та тестів. Підтверджено успішне виконання workflow на Windows, Ubuntu та macOS.

Повторний запуск `init` підтвердив можливість перевірки готового проєкту без його пошкодження. Негативний сценарій із навмисною помилкою продемонстрував здатність агента виявляти невдале тестування та повідомляти про нього.

Найважливішим результатом стало не лише створення працездатного проєкту, а й дослідження поведінки AI-агента під час реальних технічних помилок, повторних запусків і перевірок.
